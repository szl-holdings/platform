# Public Buyer Journey

**Last updated:** April 2026
**Purpose:** Map the buyer journey for SZL's three audiences

---

## Audience Segments

### 1. Technical Buyer (CTO, VP Engineering, Platform Architect)
**Motivation:** "Can this platform actually deliver what it claims?"
**Journey:**
1. Arrives via referral, GitHub, or Hacker News
2. Reads architecture documentation
3. Explores platform primitives reference
4. Tries Decision Theater interactive demo
5. Reviews open-source governance libraries on GitHub
6. Evaluates API documentation and integration patterns
7. Requests architecture deep-dive call
8. **Conversion:** Technical validation complete → champions internally

**What they need to see:**
- Real code (not marketing screenshots)
- Clean API design with Stripe-quality error envelopes
- OpenAPI spec with structured response formats
- GitHub repo with CI/CD, tests, and professional commit history
- Decision Theater with live data (not static demos)

### 2. Enterprise Buyer (CISO, COO, Compliance Director)
**Motivation:** "Will this reduce our governance risk and satisfy auditors?"
**Journey:**
1. Arrives via industry conference, analyst report, or peer referral
2. Reads trust center and security posture
3. Reviews compliance framework coverage
4. Downloads diligence packet (NDA-gated)
5. Requests demo with their domain use case
6. Evaluates audit trail and proof chain capabilities
7. Runs pilot in a single domain
8. **Conversion:** Pilot success → enterprise contract

**What they need to see:**
- Trust center with real compliance evidence (Vanta pattern)
- Proof chain demonstration with immutable records
- Role-based access control matrix
- Data encryption and residency documentation
- Export capabilities for legal discovery and compliance

### 3. Investor (VC Partner, Analyst)
**Motivation:** "Is this a real platform or a demo?"
**Journey:**
1. Arrives via pitch deck or warm introduction
2. Reviews category positioning documentation
3. Explores live platform (Decision Theater)
4. Reads architecture documentation
5. Inspects GitHub repo (commit velocity, code quality, CI/CD)
6. Reviews team and domain expertise
7. Requests diligence packet
8. **Conversion:** Technical conviction → term sheet discussion

**What they need to see:**
- Clean monorepo with 34+ shared libraries (not a monolith)
- Six platform primitives with real implementations
- Live Decision Theater (not Figma mockups)
- Market sizing ($16.3B growing 24.7% CAGR)
- Domain breadth (defense, maritime, real estate, consulting)
- Professional documentation (CHANGELOG, BRAND_GUIDELINES, SECURITY)

## Competitive Buyer Journey Patterns

### Stripe
- Self-serve signup → first API call in 5 minutes
- Beautiful documentation with inline code examples
- Test mode with real-looking data
- Gradual disclosure of complexity

### Vanta
- Trust center as first impression → compliance badge display
- Self-serve trial → immediate value (gap analysis)
- Compliance automation reduces time-to-SOC-2

### Vercel
- One-click deploy from GitHub → instant preview URL
- Dashboard shows deployment status immediately
- Progressive complexity (basic → enterprise)

### SZL Adaptation
SZL's buyer journey should combine:
- **Stripe's progressive disclosure** — start with the Decision Theater, reveal primitives incrementally
- **Vanta's trust-first impression** — trust center visible before login
- **Vercel's instant proof** — Decision Theater loads in seconds with real data
- **Palantir's enterprise gravitas** — architecture documentation conveys platform maturity
