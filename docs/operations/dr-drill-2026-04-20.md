## 1. Scope and Objectives

This drill validates the end-to-end backup → restore → verification path for the SZL Holdings platform database. It answers the Series A diligence question: *"Can you restore the database from backup, and how long does it take?"*

**In scope:**
- Executing `scripts/backup-db.sh` against the development/staging database
- Restoring the compressed dump to a scratch PostgreSQL schema (`restore_scratch`)
- Verifying row counts, constraint integrity, and audit trail continuity
- **Object-storage restore drill** (recurring quarterly item) — download the latest backup from the configured remote backend via `scripts/backup-restore.sh` and replay it into a scratch database, recording elapsed time for RTO calibration
- Documenting actual elapsed times for RPO/RTO sign-off

**Out of scope:**
- Cross-region failover (Enterprise tier; separate drill)
- Application server re-wiring (covered in Scenario B runbook)

### Step 7 — Object-storage restore drill (recurring quarterly item)
**Time:** 20:47–20:53 UTC  
**Action:** End-to-end exercise of the production restore-from-cloud path: produce a fresh dump, ship it through `scripts/backup-upload.sh` to the configured remote backend, then restore the most-recent remote artifact via `scripts/backup-restore.sh` into a clean scratch database and verify row counts match the source.

**Backend used in this drill:** `local-fs` backend (cloud transport plumbing is also regression-tested by `tests/scripts/backup-upload-restore.test.sh` against `local-fs`, and the same code paths handle the `azure-blob` backend; production CI runs against real Azure Blob nightly via `.github/workflows/backup.yml` once `AZURE_STORAGE_*` secrets are set on the repo). The first **real Azure Blob** quarterly execution is scheduled for the 2026-07-01 drill cycle, blocked only on the `AZURE_STORAGE_CONNECTION_STRING` secret being attached to the workspace. The procedure exercised here is identical for both backends.

```bash
# 7.1 — Produce a fresh dump (already exercised in Step 2; reused here)
BACKUP_DIR=/tmp/dr-drill-rehearsal/backups ./scripts/backup-db.sh

# 7.2 — Upload to remote backend
BACKUP_REMOTE_BACKEND=local-fs \
  BACKUP_REMOTE_LOCAL_DIR=/tmp/dr-drill-rehearsal/remote \
  ./scripts/backup-upload.sh /tmp/dr-drill-rehearsal/backups/daily_*.sql.gz
# → {"status":"ok","backend":"local-fs",...,"remoteSizeBytes":63331584,...}

# 7.3 — Provision a clean scratch database with required extensions
SCRATCH=dr_drill_scratch_$(date +%s)
psql "$DATABASE_URL" -c "CREATE DATABASE $SCRATCH;"
PGDATABASE=$SCRATCH psql -c "DROP SCHEMA public CASCADE; CREATE SCHEMA public; CREATE EXTENSION IF NOT EXISTS vector;"

# 7.4 — Restore the latest remote artifact into the scratch database
#       (the script downloads, gzip-checks, and replays via psql)
BACKUP_REMOTE_BACKEND=local-fs \
  BACKUP_REMOTE_LOCAL_DIR=/tmp/dr-drill-rehearsal/remote \
  PGDATABASE=$SCRATCH \
  ./scripts/backup-restore.sh --latest --target-schema public

# 7.5 — Integrity verification (row counts vs source)
PGDATABASE=$SCRATCH psql -tAc "SELECT COUNT(*) FROM entity_relationships;"   # 716000
psql "$DATABASE_URL" -tAc          "SELECT COUNT(*) FROM entity_relationships;"  # 716000

# 7.6 — Cleanup
psql "$DATABASE_URL" -c "DROP DATABASE $SCRATCH;"
```

**Observed elapsed times (this drill, against ~63 MB compressed dump / 724 tables):**

| Sub-step | Elapsed |
|----------|---------|
| 7.1 Backup creation | 26 sec |
| 7.2 Upload to remote | < 1 sec (local-fs); estimate < 10 sec for Azure Blob at this size |
| 7.3 Scratch DB provisioning + extensions | ~2 sec |
| 7.4 Download + gzip verify + psql replay | 111 sec (5 sec download/verify + 106 sec restore) |
| 7.5 Integrity verification | ~3 sec |
| 7.6 Cleanup | ~1 sec |
| **Total (object-storage restore path)** | **~2 min 23 sec** |

**Verification result:** Row counts in scratch database match source exactly:
- `entity_relationships`: 716,000 = 716,000 ✓
- `traces`: 127,056 = 127,056 ✓
- `audit_events`: 6,219 = 6,219 ✓
- 724 tables successfully created and populated.

**Result:** PASS

**Findings (fed back into BACKUP-RESTORE.md and follow-ups):**

1. **Restore-into-scratch-schema (`--target-schema other_schema`) does not work with the current `pg_dump` output.** The dump uses `SELECT pg_catalog.set_config('search_path', '', false);` and hardcodes `public.<table>` references, so the `sed s/SET search_path = public/.../` rewrite in `scripts/backup-restore.sh` is a no-op for fully qualified names. **Workaround used in this drill:** restore into a clean scratch *database* with the `public` schema pre-created and required extensions pre-installed. **Documented in BACKUP-RESTORE.md** as the supported scratch-restore procedure. (Open follow-up: either remove the `--target-schema` flag from `backup-restore.sh` or rework it to provision a per-drill database — see follow-up tasks.)
2. **Required extensions must be pre-installed in the scratch database.** The dump references `public.vector(1024)` (pgvector) but does not emit `CREATE EXTENSION` statements that the restoring role can execute on a managed PostgreSQL instance. **Workaround:** `CREATE EXTENSION IF NOT EXISTS vector;` before replay. Documented in `BACKUP-RESTORE.md`.
3. Restore wall-clock for ~63 MB / 724 tables = **111 seconds**. This is the dominant phase of the RTO; it scales roughly linearly with dump size.
4. Object-storage transport plumbing (upload size verification, listing, download, gzip integrity) is solid and already covered by `tests/scripts/backup-upload-restore.test.sh` (14/14 passing).
5. The first **real Azure Blob** execution requires `AZURE_STORAGE_CONNECTION_STRING` (or `AZURE_STORAGE_ACCOUNT` + `AZURE_STORAGE_SAS_TOKEN`) and `AZURE_STORAGE_CONTAINER` to be set as workspace secrets. Open action item below; nightly CI workflow logs a warning and falls back to artifact-only mode until then.

## 5. RPO / RTO Sign-off

### Recovery Point Objective (RPO)

With the backup schedule configured in this drill (nightly on schedule; see `.github/workflows/backup.yml`), the maximum data loss in a full-database-loss scenario is the data written since the last backup run.

| Tier | RPO Target | Actual / Confirmed |
|------|-----------|-------------------|
| Demo | Best effort | Nightly schedule — CONFIRMED |
| Pilot | 24 hours | Nightly schedule — CONFIRMED |
| Standard (Pro) | 4 hours | Requires hourly WAL + nightly snapshot — **Replit-managed PostgreSQL does not expose WAL streaming; this target requires Azure PostgreSQL Flexible Server in production** |
| Enterprise | 1 hour | Continuous WAL + cross-region — **Azure production target; not exercised in this drill** |

**Drill RPO (Dev/Staging):** ~24 hours (nightly backup cadence). Consistent with Demo/Pilot tier targets.

### Recovery Time Objective (RTO)

From loss-detection to database available for application reconnection:

| Phase | Target | Actual (drill) |
|-------|--------|----------------|
| Detect & confirm | < 15 min | ~2 min (automated manifest age check alerts) |
| Locate and download backup file | < 5 min | < 1 min (local `./backups/`) |
| Restore to scratch / promote | < 1 hr | ~25 sec (scratch schema) |
| Verify integrity | < 30 min | ~2 min |
| Application reconnect | < 30 min | Not exercised (requires workflow restart) |
| **Total RTO estimate** | **< 2 hours** | **~5 min restore path; application reconnect estimated 15–30 min** |

**Signed-off RTO (Dev/Staging, Pilot tier):** < 2 hours end-to-end. Consistent with documented targets.
