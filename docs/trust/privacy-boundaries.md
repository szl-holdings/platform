# SZL Holdings — Privacy Boundaries

**Date:** April 2026

---

## Data Classification

SZL Holdings classifies all data handled by the platform into four tiers:

| Tier | Label | Description | Access |
|------|-------|-------------|--------|
| 1 | **Public** | Publicly available data (NYC Open Data, AIS public feeds, public financial filings) | Any authenticated user |
| 2 | **Internal** | Operational data generated by platform use (signals, workflows, metrics) | Role-dependent |
| 3 | **Confidential** | Customer-specific data, PII where applicable, financial data | Elevated role required |
| 4 | **Restricted** | Credentials, secrets, security configurations | System/admin only |

---

## Data Handling Principles

**Purpose limitation.** Data collected by SZL platforms is used to deliver the service for which it was collected. Operational data is not used for advertising, is not sold, and is not shared with third parties except as required to deliver the service (e.g., payment processing via Stripe, email delivery via Resend/SendGrid).

**Data minimization.** We collect the minimum data necessary for the platform to function. Fields that are optional in schema design remain optional in practice.

**Retention.** Data retention periods are defined per data class. Data beyond retention windows is purged on schedule. Platform logs are retained for a defined period and then rotated.

**Access control.** Access to data is determined by role assignment. Users cannot access data outside their organizational scope.

---

## Personally Identifiable Information (PII)

Current PII handling in the platform:

| Data Element | Where | Purpose | Storage |
|-------------|-------|---------|---------|
| Name, email | Authentication (OIDC) | Identity and session management | Session store (short TTL) |
| Contact information | Carlota Jo inquiry form | Client engagement | PostgreSQL (encrypted at rest) |
| User actions | Audit trail | Operational accountability | PostgreSQL (immutable, append-only) |

**No financial data** is stored directly by SZL platforms — payment processing is fully delegated to Stripe.

## Third-Party Data Processors

| Service | Purpose | Data Shared |
|---------|---------|------------|
| Replit | Hosting platform | Application code, environment secrets (encrypted), database |
| Azure | Enterprise hosting | Application code, encrypted configuration |
| Stripe | Payment processing | Customer billing information (Stripe manages PCI compliance) |
| OpenAI / Anthropic / Gemini | AI inference | Prompt content (no PII in prompts by policy) |
| Resend / SendGrid | Transactional email | Recipient email addresses |
| Mapbox | Map rendering | Geographic coordinates (for Terra property maps, Vessels fleet tracking) |

All third-party integrations are reviewed before onboarding. API credentials are scoped to minimum required permissions.

---

## Demo and Simulation Data

Platform dashboards visible in this codebase reference seeded or simulated data for demonstration purposes. This data:
- Does not represent real users, real vessels, real properties, or real security incidents
- Is explicitly labeled within each application (Demo / Pilot / Live badges)
- Is generated by seed scripts in `scripts/`

The infrastructure, schemas, APIs, and interfaces are designed for real workloads. Data state does not represent capability.
