## Overview

Two of the five platform primitives — **Proof Chain** and **Covenant Policy** — define how trust is enforced across the SZL Holdings ecosystem. Together, they ensure that:

1. Every consequential action has a verifiable audit trail (Proof Chain)
2. Every consequential action requires appropriate authorization (Covenant Policy)
3. AI outputs carry provenance metadata and export safety controls (Proof Chain)
4. Human-in-the-loop is structural, not optional (Covenant Policy)

This document explains how these two primitives work together, what users and admins see, and how trust flows through the platform.

## Proof Chain — How Trust Is Recorded

### What Users See

When an operator views a recommendation, a document, or an AI-generated analysis, they see provenance metadata:

- **Source** — who or what generated this content (human, AI model, system, external feed)
- **Confidence** — calibrated confidence score (if AI-generated)
- **Evidence** — linked source documents and data points
- **Review status** — whether this content has been reviewed and approved
- **Export safety** — whether this content is cleared for external use

In PRISM Counsel, for example, a case summary generated by the AI copilot shows:
- "Generated by AI (Qwen3-8B) at 2026-04-15 14:23"
- "Based on: 3 court filings, 2 client documents, 1 prior case analysis"
- "Review status: Pending human review"
- "Export safety: Restricted (not cleared for client distribution)"

### What Admins See

Administrators and compliance officers access the full proof chain:

- Complete provenance history for any content item
- Chain of custody: creation → edits → reviews → approvals → exports
- Actor attribution at every step (who did what, when)
- Version history with diff capability
- Export audit log (who exported what, to whom, when)

### How Proofs Are Created

```
Content creation event
    │
    ├── AI generates content ──▶ tagAIContent()
    │     • Records model, prompt hash, source class
    │     • Links to parent proof (if derived from prior content)
    │     • Sets initial export safety to "pending_review"
    │
    ├── Human authors content ──▶ tagAIContent(source: "human_authored")
    │     • Records author, timestamp
    │     • Sets export safety based on classification
    │
    └── System computes content ──▶ tagAIContent(source: "system_computed")
          • Records algorithm, input data references
          • Sets export safety based on data classification
```

### Export Safety Flow

Before any content can be sent to a client, included in a report, or exported from the platform:

```
Content ready for export
    │
    ▼
isExportSafe(proofId) ──▶ Check review status
    │                         │
    ├── safe ────────────────▶ Proceed with export
    │                         
    ├── restricted ──────────▶ Internal use only (block external export)
    │                         
    ├── pending_review ──────▶ Require human review first
    │                         
    └── blocked ─────────────▶ Cannot be exported (flagged or retracted)
```

## Covenant Policy — How Trust Is Enforced

### What Users See

When an operator attempts a consequential action, the Covenant Policy engine determines what happens:

**Permitted actions** execute immediately:
- The action proceeds
- A proof chain entry is recorded
- The operator sees confirmation

**Actions requiring approval** enter the approval queue:
- The operator sees "Awaiting approval from [role/person]"
- The approver receives a notification (Lyte web, CORTEX mobile, or email)
- The action is held until approved or denied

**Denied actions** are blocked:
- The operator sees a clear explanation of why the action was denied
- No proof chain entry is created for the attempted action
- The denial is logged for audit purposes

### What Admins See

Policy administrators can:

- View all active policies and their conditions
- See which actions require approval and from whom
- Review the approval queue and historical decisions
- Create new policies using templates or custom rules
- Audit policy enforcement history

### Policy Structure

A Covenant Policy consists of rules that match requests to decisions:

```
Policy: "AI Agent Execution Controls"
├── Rule 1: ALLOW agents to generate recommendations (no approval needed)
├── Rule 2: ESCALATE if agent wants to execute a financial transaction (requires manager approval)
├── Rule 3: ESCALATE if agent wants to modify a legal matter status (requires analyst + manager)
└── Rule 4: DENY agents from deleting audit records (always blocked)
```

### Policy Templates

Pre-built templates for common governance scenarios:

| Template | Domain | What It Governs |
|----------|--------|----------------|
| `ai_advisory_standard` | All | AI agents can recommend but not execute |
| `financial_approval_chain` | Lyte | Financial transactions require dual approval |
| `legal_matter_governance` | PRISM Counsel | Matter status changes require review |
| `vessel_sanctions_response` | Vessels | Sanctions alerts require immediate review |
| `security_incident_response` | Aegis | Incident escalation and response policies |
| `client_communication_review` | Carlota Jo | Client-facing content requires approval |

### Approval Flow

```
Action requested
    │
    ▼
Covenant Policy Engine ──▶ checkPermission(request)
    │
    ├── PERMIT ──────────────▶ Execute action ──▶ Record in Proof Chain
    │
    ├── ESCALATE ────────────▶ Create ApprovalRequest
    │                              │
    │                              ▼
    │                         Notify approver(s)
    │                              │
    │                         ┌────┴────┐
    │                         │         │
    │                     Approved    Denied
    │                         │         │
    │                    Execute    Block + log
    │                         │
    │                    Record in Proof Chain
    │
    └── DENY ────────────────▶ Block action ──▶ Log denial
```

## How Proof Chain and Covenant Policy Work Together

The two primitives form a trust sandwich:

1. **Before action:** Covenant Policy checks permission and approval requirements
2. **During action:** Every step is recorded in the Proof Chain
3. **After action:** The Outcome Graph tracks whether the action achieved its goal
4. **On review:** Compliance officers can reconstruct the full chain from the Proof Chain

### Example: AI-Assisted Legal Case Summary

1. PRISM Counsel AI copilot generates a case summary
2. `tagAIContent()` creates a Proof Chain entry → status: `pending_review`, export: `restricted`
3. Attorney reviews the summary in the copilot workbench
4. `reviewProof()` updates status to `approved`, export remains `restricted` (internal only)
5. Attorney requests to send summary to opposing counsel
6. `checkPermission()` evaluates against `client_communication_review` policy → result: `ESCALATE`
7. Senior partner receives approval request
8. Senior partner approves → `reviewApproval()` records the decision
9. `reviewProof()` updates export safety to `safe`
10. Summary is exported → export event recorded in Proof Chain
11. Full trail is available: AI generation → attorney review → partner approval → export

### Example: Dark Vessel Sanctions Alert

1. Vessels detects AIS anomaly → PRISM Bus publishes `domain_signal`
2. Workflow Engine starts `sanctions_review` process
3. Monte Carlo simulates financial exposure under different scenarios
4. AI agent recommends freezing trade activity → `recordRecommendation()`
5. Covenant Policy checks `vessel_sanctions_response` → result: `ESCALATE`
6. Compliance officer receives approval in CORTEX mobile
7. Compliance officer approves → action executes
8. Proof Chain records the full trail with actor attribution, timestamps, and evidence references
9. Outcome tracked: was the sanctions concern valid? Outcome Graph records the result and feeds back into agent calibration

## Trust Guarantees

| Guarantee | How It Is Enforced |
|-----------|-------------------|
| AI cannot execute consequential actions autonomously | Covenant Policy gates all AI-triggered mutations |
| Every AI output has provenance | Proof Chain `tagAIContent()` is called for all AI-generated content |
| Content cannot be exported without review | `assertExportSafe()` guards all export paths |
| Every approval is attributed | `reviewApproval()` records reviewer identity, timestamp, and rationale |
| The audit trail is immutable | Proof Chain entries are append-only — updates create new entries, not modifications |
| Policies are version-controlled | Policy changes are themselves recorded in the Proof Chain |

## User-Facing Trust UI

The trust primitives are now surfaced in product UI across Aegis, Terra, and Vessels through reusable React components in `lib/shared-ui`:

### ProofPanel Component

Renders proof chain metadata inline in any AI output area:

```tsx
<ProofPanel
  proof={{
    sourceClass: "llm_generated",
    confidenceScore: 0.87,
    modelId: "gpt-4o",
    reviewState: "approved",
    exportSafetyState: "safe",
    inputSources: [{ type: "threat_feed", id: "001", label: "CISA Advisory" }],
    lineage: [{ label: "Raw logs ingested", sourceClass: "sensor_data" }],
  }}
  variant="inline"   // "inline" | "drawer" | "badge"
  showActions        // enables Approve / Flag buttons for reviewers
  onReview={(state) => reviewProof({ proofId, reviewState: state })}
/>
```

**Variants:**
- `"badge"` — compact inline chip with popover expansion (for AI output panels)
- `"inline"` — full provenance card embedded in content
- `"drawer"` — sidebar panel for detailed review

### PolicyResult Component

Shows policy evaluation outcomes with full context:

```tsx
<PolicyResult
  decision={{
    effect: "escalate",
    reason: "Requires CISO approval for external notification",
    escalationPath: ["SOC Lead", "Security Manager", "CISO"],
    approvalHistory: [...],
    whatNeedsToChange: ["CISO must approve", "Legal review required"],
  }}
  showDetails
  onEscalate={() => triggerEscalation(requestId)}
  onAppeal={(reason) => submitAppeal(requestId, reason)}
/>
```

### AdminAuditTrail Component

Full decision timeline with filtering, search, and immutable hash verification:

```tsx
<AdminAuditTrail
  entries={auditEntries}
  showFilters
  domainLabel="Security Operations"
/>
```

### SimulationCockpit Component

Decision cockpit with scenario ranges, sensitivity analysis, cost-of-waiting, and predicted vs actual tracking:

```tsx
<SimulationCockpit
  title="Incident Response Decision Cockpit"
  scenarios={[worstCase, baseCase, bestCase]}
  primaryMetricLabel="Time to Containment"
  iterationsRun={10000}
  confidenceLevel={0.95}
  predictedVsActual={[...pastOutcomes]}
/>
```
