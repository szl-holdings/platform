## C) Strongest implementation-level counterexample

**TOCTOU on revocation: "authority at dispatch time" may not be supported by the existing interface.** Kimi's slice 1 requires the revoked-grant case (1.3) and the outage case (1.4) to deny *before dispatch*, i.e., authority re-evaluated at dispatch time against current revocation state. But if the existing RoutePolicy/RouteGrant path evaluates revocation once at admission/decision and the result is what gets receipted, then a revocation landing **after decision-commit but before the provider call** would fail open while the receipt still records an ordered, plausible-looking decision chain. The fixture as specified cannot detect this unless the router has a dispatch-time re-check hook — which I could not confirm exists (`MISSING_INTERFACE` at row 1.2/1.3).

- **Concrete falsifier:** in the case-3 fixture, revoke the grant in the window between the decision record and the mock provider invocation (e.g., via a test hook on the spy). Expected: provider-call count 0 and decision = DENY with revocation evidence. If the spy records 1 call, the "denied before dispatch" claim is false and slice 1 is `BLOCKED:revocation-toctou` until a dispatch-time re-check hook is added to szl-router.
- **Runner-up (secondary, with falsifier):** slice 2's ambiguous post-dispatch failure without an idempotency key must be deterministic for slice 3's `VALID` digest to be stable. Falsifier: run the clean verifier twice over the same bundle including the parked ambiguous case; if the before/after ledger-state hash differs across runs (e.g., because parking writes a timestamped tombstone into the hashed state), `r4-verification.json` cannot hold a reproducible `VALID` ⇒ `BLOCKED:nondeterministic-ledger-hash`. Mitigation: hash only canonical, mutation-excluded fields; define in the fixture spec.

## D) Mistral-checks-Kimi verdict

1. **Slice 1 — implementable, contingent.** All four cases are implementable against a RoutePolicy/RouteGrant-shaped interface, *provided* a dispatch-time revocation re-check exists or is added (counterexample C). Timing semantics are coherent: decision → (re-check) → dispatch ordering is well-defined. Fail-closed on status outage is correct, with one recorded caveat: case 4 makes the revocation/status probe a **synchronous availability dependency of dispatch itself** — allowed requests will also be denied during an outage. That must be stated in the trust boundary, not discovered later.
2. **Slice 2 — implementable; idempotency semantics coherent with one sharpening.** The seven-case matrix is complete for the stated falsifiers. Coherence requires the ambiguous-no-key case to be *parked, never retried, and deterministic* (see C runner-up); the plan's falsifier implies it but does not state the expected terminal state explicitly — recommend the fixture spec pin `AMBIGUOUS_PENDING` as the only legal outcome. Provider-cost vs customer-charge separation is correctly required and must be enforced in the receipt schema, not just prose.
3. **Slice 3 — implementable.** `uv lock --check` plus digest capture is concrete and fail-closed; the envelope's `BLOCKED`-on-red-build rule matches the lane's deployed fail-closed rewrite (revision `5b6bc7119a…`, caller-supplied). The byte-hash verifier with the four-mutation matrix is feasible within the adopted evidence-core disciplines and correctly defers NovaFabric breadth. No requirement assumes an interface outside the three repos.
4. **No duplicate scopes detected:** the lane split (Kimi = fixture semantics/mutations; Mistral = this map + handoff mechanics) is respected here — this document adds no schema and no parallel plan.
5. **Overall:** candidate for `ACCEPT_FOR_CI` with two recorded conditions: (i) row 1.2/1.3 dispatch-time re-check resolved as hook-or-`BLOCKED:revocation-toctou`; (ii) ambiguous-case terminal state pinned as `AMBIGUOUS_PENDING` with deterministic hashing.
