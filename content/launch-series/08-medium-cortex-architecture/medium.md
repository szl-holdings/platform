# CORTEX Architecture — How Unified Mobile Command Surfaces Cross-Domain Intelligence

*Medium · Platform Engineering Series · April 29, 2026*

---

The central challenge of multi-domain operations is not information abundance. It is context switching.

An operator responsible for fleet decisions, real estate portfolio health, and security posture simultaneously does not need three separate dashboards. They need one interface that surfaces what matters most — across all three domains — without requiring them to know in advance which domain is producing the most consequential signal at any given moment.

This is the problem CORTEX was built to solve.

---

## What CORTEX Is

CORTEX is the unified mobile command layer for the SZL Holdings platform — a native iOS and Android application that surfaces cross-domain intelligence, governed decision queues, and action workflows across all six domain packs in a single interface.

It is not a mobile version of the desktop command surface. It is a distinct interface designed for the operating context of mobile: partial attention, time-compressed decisions, cross-domain badge awareness, and the need to confirm or escalate consequential actions quickly without losing context.

The architectural claim is specific: CORTEX is the same governance infrastructure — the same six primitives, the same Covenant Policies, the same Proof Chain writes, the same Outcome Graph updates — delivered through an interface optimized for mobile decision-making.

The governance does not change depending on which interface the operator is using. A Covenant Policy that requires senior authorization for a containment action applies identically on the mobile app and the desktop surface. The Proof Chain record from a mobile-confirmed action is structurally identical to a record from a desktop confirmation.

This is the non-obvious property of CORTEX: not that governance follows the operator to mobile, but that the platform's governance structure is interface-agnostic by design.

## The Cross-Domain Badge Layer

The primary mobile UX pattern is the cross-domain badge: a notification surface that surfaces the aggregate exception count and urgency score across all domains simultaneously.

An operator waking up at 6am sees:

- Aegis: 2 active alerts requiring attention
- Vessels: 1 voyage exception with estimated cost impact >$40k
- Terra: 3 distress leads scored above acquisition threshold
- PRISM Counsel: 1 document requiring review authorization

These are not push notifications. They are structured exception aggregates, pulled from the Event Fabric in real time, ranked by a cross-domain urgency model that understands the operator's role permissions, the organizational risk posture defined in Covenant Policy, and the historical priority patterns recorded in the Outcome Graph.

The operator does not need to open four separate apps to understand their morning exception queue. CORTEX surfaces it as a single ranked list, with enough context at the badge level to triage without drilling into each domain.

## Governed Action Confirmation on Mobile

The second mobile UX pattern is the governed action confirmation: the ability to confirm or escalate a consequential action from the mobile interface, with the full governance guarantees of the platform applied.

This has a specific security architecture requirement. Confirming a containment action, authorizing an acquisition workflow, or escalating a security incident from a mobile device must be:

- **Biometrically authenticated** — Face ID or Touch ID required for any action that crosses a Covenant Policy confirmation threshold
- **Context-preserved** — The full evidence chain that led to the recommendation must be surfaced on the confirmation screen, not just the summary
- **Policy-evaluated at confirm time** — The Covenant Policy check runs at the moment the operator confirms, not at the moment the recommendation was generated, to catch policy state changes that may have occurred between recommendation and confirmation
- **Proof Chain-complete** — The confirmation record includes the biometric authentication event, the device identifier, the operator's current role state, and the evidence chain as presented at the time of confirmation

This last point is architecturally significant. The Proof Chain record for a mobile confirmation includes not just who confirmed, but what they saw when they confirmed — the specific version of the evidence chain that was presented to the operator on the confirmation screen. This eliminates the ambiguity in standard approval workflows where the approver may have seen stale information.

## The Intelligence Briefing Surface

The third mobile interface pattern is the daily intelligence briefing — a structured summary generated by the CORTEX reasoning layer each morning, drawing from the Outcome Graph and Event Fabric to surface:

- Active exceptions ranked by urgency and estimated impact
- Trend signals emerging across domains (flight path of distress scores, alert volume trajectory, voyage exception frequency)
- Action items pending authorization
- Yesterday's closed decisions and their outcomes

The briefing is not a static report. It is a queryable interface — the operator can drill into any item for full context, run a simulation on any open decision, or confirm or escalate any pending action from the briefing surface directly.

The CORTEX reasoning layer does not generate the briefing from scratch each morning. It draws from the Outcome Graph's accumulated decision history, the Event Fabric's current signal state, and the Covenant Policy's view of what requires operator attention at the current authorization level. The briefing is a synthesis of the platform's current state, not an independent analysis.

## The Biometric Authentication Architecture

Biometric authentication in CORTEX is not simply Face ID as a login gate. It is a governance checkpoint integrated into the action confirmation flow.

The authentication model has three tiers:

**Session authentication** — Face ID or Touch ID to open the application. Standard mobile security pattern. Does not in itself authorize any consequential action.

**Action authentication** — A second biometric check required for any action that triggers a Covenant Policy requiring explicit confirmation. The operator is confirming not just "I am who I say I am" but "I am consciously authorizing this specific action, having reviewed this specific evidence."

**Elevated action authentication** — For actions at the highest policy threshold — cross-domain escalations, identity suspension actions, actions above a financial consequence threshold — a time-bound confirmation code is required in addition to biometric authentication, creating a two-factor authorization event.

Each authentication event is recorded in the Proof Chain with a device fingerprint, an authentication method identifier, and a timestamp — providing a complete provenance record for any dispute about whether a mobile confirmation was made knowingly.

## The Architecture Summary

CORTEX is built on four architectural principles:

**Interface-agnostic governance** — The platform's governance guarantees do not degrade on mobile. Covenant Policy, Proof Chain, and Outcome Graph operate identically regardless of the interface.

**Cross-domain aggregation by urgency** — The mobile interface's primary value is the cross-domain badge layer: a single ranked exception queue across all domains, with enough context for triage without full drill-down.

**Confirmation-first UX** — Every consequential action requires explicit confirmation, with the full evidence chain surfaced and a biometric authentication checkpoint. The interface is designed to make confirmation deliberate, not inadvertent.

**Offline-aware state management** — CORTEX maintains a local state snapshot for the domains the operator has active permissions for, allowing triage and review even when connectivity is limited. Confirmation actions queue for execution when connectivity is restored, with the confirmation record timestamped at the time the operator made the decision.

---

## Why This Architecture Matters

The argument for CORTEX is not that mobile is becoming more important (it obviously is). It is that governance requirements do not stop at the desktop boundary.

An organization that has built governed decision infrastructure at the desktop level but allows mobile confirmations without equivalent governance is creating a gap in their accountability record — a class of consequential decisions made through an unstructured interface, without Proof Chain coverage, without Covenant Policy enforcement.

CORTEX closes that gap. The governance travels with the operator because it is platform-level, not interface-level.
